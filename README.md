# OnlineStore

An online store built with ASP.NET Core MVC (.NET 8): a public storefront with a cart and orders, and an
administrator area for managing the catalog. Authentication is delegated to Keycloak (OpenID Connect);
visitors sign in with a phone number and a one-time code. The UI is available in English and Kazakh.

## Features

**Storefront** (`/`)
- Product catalog with paging and search, product page with images.
- Cart (add / remove products), checkout and the visitor's order history.
- Visitor sign-in by phone number + one-time code; the visitor account is provisioned in Keycloak automatically.
- Language switch (English / Қазақша) and a dark theme.

**Administrator area** (`/Administrator`)
- Products ("Warehouse"): list, add, edit, image upload, stock quantity — roles `root` and `employee`.
- Categories: create, edit, delete — role `root`.
- Link to the Keycloak admin console for user management — role `root`.
- Storybook: a sandbox page with sample UI components (TodoItem demo) — role `root`.

## Architecture

The solution follows a layered (Clean Architecture-style) structure. Dependencies point inwards:

```
OnlineStore (MVC)  ──►  Application  ──►  Domain
      │                     ▲
      ├──► Infrastructure ──┤
      ├──► Persistence ─────┘
      └──► KeycloakExtension
```

- **Domain** — entities (`Products`, `Orders`, `TodoItem`), enums, value objects and specifications. No infrastructure dependencies.
- **Application** — use cases as MediatR commands/queries (`UseCases/<Feature>/{Commands,Queries}/<Name>/`), DTOs,
  validators, repository and service interfaces.
- **Persistence** — `AppDbContext`, entity configurations, repositories, EF Core migrations.
- **Infrastructure** — service implementations (e.g. visitor sign-in via Keycloak).
- **KeycloakExtension** — cookie + OIDC authentication setup, Keycloak admin/token clients, role constants.
- **Resource** — localization resources (`.resx`).
- **OnlineStore** — controllers, Razor views, the `Administrator` area, middleware, filters, frontend sources.

Request flow: controller → `IMediator` → `ValidationPipelineBehavior` (FluentValidation + async business checks)
→ handler → repository. Handlers return `Result`; validation failures throw `ApplicationException`, which
`ApplicationExceptionFilter` turns into HTTP 400 with the message as the response body (other exceptions → 500).

Composition root: `OnlineStore/Program.cs` (`AddKeycloak` → `AddPersistance` → `AddInfrastructure` → `ConfigureMediator`).

## Running with Docker Compose

The quickest way to get the whole stack (SQL Server, Keycloak with the `web-net` realm, Seq, the app and Caddy with HTTPS):

```bash
cp .env.example .env    # set DOMAIN, passwords and client secrets (openssl rand -hex 24)
docker compose up -d --build
docker compose logs -f app
```

- Store: `https://DOMAIN/`, Keycloak: `https://DOMAIN/auth` (admin console: `https://DOMAIN/auth/admin`).
- The app applies EF Core migrations on startup (`Database__MigrateOnStartup=true`).
- The imported realm has no users: create one in the Keycloak console (realm `web-net`) and assign the realm role `root`.
- For a local network / VM without internet access use `CADDY_TLS=internal`.

Full guide (server requirements, backups, SQL Server access, maintenance): [deploy/README.md](deploy/README.md).

## Local development

### Prerequisites

- .NET 8 SDK
- Node.js 20 (npm 10)
- SQL Server (local instance or container)
- Keycloak 26.1.4 with the `web-net` realm
- Seq (optional — without it logs still go to the console)
- `dotnet-ef` for migrations: `dotnet tool install --global dotnet-ef`

### 1. Infrastructure

The easiest option is to start only the infrastructure services from `docker-compose.yml`:

```bash
docker compose up -d sqlserver sqlserver-init keycloak seq
```

Note that this Keycloak instance is configured for the public `https://DOMAIN/auth` URL. For a plain local setup
you can run a standalone Keycloak and import the realm from `deploy/keycloak/web-net-realm.json`; the file expects
the environment variables `APP_PUBLIC_URL` (e.g. `http://localhost:5000`), `MVC_CLIENT_SECRET` and
`BACKEND_ADMIN_CLIENT_SECRET`:

```bash
docker run -d --name keycloak -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=<admin-password> \
  -e APP_PUBLIC_URL=http://localhost:5000 \
  -e MVC_CLIENT_SECRET=<secret> -e BACKEND_ADMIN_CLIENT_SECRET=<secret> \
  -v "$(pwd)/deploy/keycloak:/opt/keycloak/data/import:ro" \
  quay.io/keycloak/keycloak:26.1.4 start-dev --import-realm
```

`start-dev` uses Keycloak's embedded database; to store data in SQL Server add the `KC_DB*` variables as in `docker-compose.yml`.

### 2. Local configuration

Do not put secrets into `appsettings.json`. Create `OnlineStore/appsettings.Local.json` (ignored by git, loaded
on top of `appsettings*.json`) or use environment variables:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=localhost,1433;Database=OnlineStore;User Id=sa;Password=<password>;TrustServerCertificate=True;"
  },
  "Authentication": {
    "Authority": "http://localhost:8080/realms/web-net",
    "ClientSecret": "<MVC_CLIENT_SECRET>"
  },
  "KeycloakProvisioning": {
    "BaseUrl": "http://localhost:8080",
    "AdminClientSecret": "<BACKEND_ADMIN_CLIENT_SECRET>",
    "UserTokenClientSecret": "<MVC_CLIENT_SECRET>"
  }
}
```

### 3. Build and run

```powershell
# frontend (from OnlineStore/Scripts)
npm ci
npm run build:dev

# backend (from the repository root)
dotnet restore OnlineStore.sln
dotnet build OnlineStore.sln --no-restore
dotnet ef database update --project Persistence/Persistence.csproj --startup-project OnlineStore/OnlineStore.csproj
dotnet run --project OnlineStore/OnlineStore.csproj
```

The `http` launch profile listens on `http://localhost:5000` (`https` profile: `https://localhost:7230`) with
`ASPNETCORE_ENVIRONMENT=Local`. Instead of `dotnet ef database update` you can set `Database:MigrateOnStartup=true`.

Run `npm run dev` in `OnlineStore/Scripts` to rebuild bundles on change while working on the frontend.

## Configuration

Configuration sources (later ones win): `appsettings.json` → `appsettings.{Environment}.json` →
`appsettings.Local.json` → environment variables → command-line arguments. Environment variables use `__` as the
section separator (e.g. `Authentication__ClientSecret`).

| Key | Purpose |
|---|---|
| `ConnectionStrings:DefaultConnection` | SQL Server connection string of the application DB |
| `Database:MigrateOnStartup` | apply EF Core migrations on startup (`true` in docker-compose) |
| `Authentication:Authority` | Keycloak realm URL used for OIDC |
| `Authentication:ClientId` / `ClientSecret` | OIDC client (`mvc-template`) |
| `KeycloakProvisioning:BaseUrl` | Keycloak base URL used by the backend |
| `KeycloakProvisioning:PublicUrl` | Keycloak URL for the browser (admin console link) when it differs from `BaseUrl` |
| `KeycloakProvisioning:Realm` | realm name (`web-net`) |
| `KeycloakProvisioning:AdminClientId` / `AdminClientSecret` | service account client for the Admin API (`backend-admin`) |
| `KeycloakProvisioning:UserTokenClientId` / `UserTokenClientSecret` | client used to issue visitor tokens (`mvc-template`) |
| `KeycloakProvisioning:VisitorRealmRole` | realm role assigned to visitors (`visitor`) |
| `KeycloakProvisioning:VisitorEmailDomain` | domain for technical e-mails of visitors without an e-mail |
| `Serilog` | log levels and sinks (Seq URL: `Serilog:WriteTo:1:Args:serverUrl`) |

Docker Compose variables are documented in [.env.example](.env.example).

## Database and migrations

The EF Core context and migrations live in `Persistence`. After changing the domain model or entity configurations, add a migration:

```powershell
dotnet ef migrations add <MigrationName> --project Persistence/Persistence.csproj --startup-project OnlineStore/OnlineStore.csproj
```

Apply it locally:

```powershell
dotnet ef database update --project Persistence/Persistence.csproj --startup-project OnlineStore/OnlineStore.csproj
```

Do not modify migrations that have already been applied; add a new one instead.

## Frontend

Sources are in `OnlineStore/Scripts/src/`; webpack writes the output to `OnlineStore/wwwroot/js/` (generated, not committed).

| Command (from `OnlineStore/Scripts`) | What it does |
|---|---|
| `npm ci` | install dependencies |
| `npm run build:dev` | fast development build (no minification, no type checking) |
| `npm run build` | production build (Terser + CssMinimizer) with type checking |
| `npm run dev` | development build in watch mode |
| `npm run typecheck` | TypeScript type check only |

Conventions:
- Every `.ts` file under `src/` becomes its own bundle at `wwwroot/js/src/<same path>.bundle.js` (SCSS → `.css` next to it).
- Page scripts mirror the view path: `src/views/home/cart/index.ts` → `Views/Home/Cart.cshtml`,
  `src/areas/administrator/views/products/add.ts` → `Areas/Administrator/Views/Products/Add.cshtml`.
- `src/index.ts` / `index.css` are loaded on every page by both layouts, together with the shared
  `vendors.bundle.js` (all `node_modules` code) and `runtime.bundle.js`.
- Shared helpers live in `src/utils/` (HTTP client, toaster, modal, localization, cart, visitor auth, dark theme)
  and `src/shared/` (paged table).

## Authentication and roles

- Cookie authentication with the Keycloak OIDC challenge (`/Account/Login`, callback `/signin-oidc`).
- Realm `web-net`, clients `mvc-template` (the app) and `backend-admin` (service account for the Admin API).
- Realm roles (`KeycloakExtension/RoleConstants.cs`):

| Role | Access |
|---|---|
| `root` | the whole administrator area, including categories, Storybook and user management |
| `employee` | administrator area: dashboard and products |
| `visitor` | storefront account: cart, checkout, orders |

Visitor sign-in: the visitor requests a code for a phone number, then submits it; the backend validates the code,
creates or updates the user in Keycloak with the `visitor` role and signs them in. In the current implementation
the code is **written to the application log** (`LoggingVisitorCodeSender`) — replace `IVisitorCodeSender` with
an SMS provider for production use.

Staff accounts (`root`, `employee`) are created in the Keycloak admin console.

## Localization

- Supported cultures: `en` (default) and `kk`. The current culture is stored in the `culture` cookie and switched via `/Culture/ChangeLanguage?locale=kk`.
- Server-side strings: `Resource/SharedResources.resx` and `Resource/SharedResources.kk.resx`.
- Client-side strings: `utils/localization` loads them from `/Culture/GetResources` and exposes `t(key, fallback)`.
- When adding a string, add the key to both `.resx` files.

## Logging

Serilog writes to the console and to Seq (`http://localhost:5341` by default). Logs are enriched with the current
user (`SerilogUserEnricherMiddleware`). In Docker Compose the Seq UI is published only on the server's localhost:
open it through an SSH tunnel (`ssh -L 5341:localhost:5341 user@server`).
